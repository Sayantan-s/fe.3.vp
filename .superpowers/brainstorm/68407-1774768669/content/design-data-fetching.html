Design — Section 3: Data Fetching & Loading States

Concurrent client-side fetching, skeletons, and error handling

Fetching Strategy

Concurrent fetch inside providers
// Each provider fetches its own data independently on mount
// Both fire concurrently since they're sibling providers

VideoDataProvider (videoId)
└─ useEffect on mount
└─ fetch(`/api/video/${videoId}`)
└─ on success → setState({ videoUrl, bg, padding, rounding, isLoading: false })
└─ on error → setState({ error: message, isLoading: false })

TranscriptProvider (videoId)
└─ useEffect on mount
└─ fetch(`/api/video/${videoId}/transcript`)
└─ on success → setState({ text, words, isLoading: false })
└─ on error → setState({ error: message, isLoading: false })

// Both fetches fire in the same tick — truly concurrent
// No waterfall, no shared loading state

Loading State Layers

Three layers of loading UI
Layer 1: Route-level
@leftPanel/loading.tsx
@rightPanel/loading.tsx
Full skeleton for each slot while the JS chunk loads. Handled by Next.js automatically via parallel routes.
Layer 2: Data-level
Context isLoading flag
Components read useVideoDataState().isLoading and render skeleton UI inline. This covers the gap between "JS loaded" and "API data arrived".
Layer 3: Component-level
Suspense around lazy Player
Player is React.lazy loaded. Its Suspense fallback shows a player-shaped skeleton while the Three.js bundle downloads.

Error States

Error handling strategy
Route-level errors (error.tsx)
→ Catches render errors, unhandled throws
→ Shows "Something went wrong" with retry button
→ Each slot has its own — one panel failing doesn't break the other

Data-level errors (context)
→ Fetch failures set error in state: { error: "Video not found", isLoading: false }
→ Components read useVideoDataState().error and show inline error UI
→ Independent per domain — transcript error doesn't affect player

// Error independence is a key benefit of the split context approach.
// Transcript API 500 → left panel shows error, player keeps working.
